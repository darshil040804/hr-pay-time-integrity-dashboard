# Functional Design Specification

**HR Pay & Time Integrity Dashboard**

> All data is synthetic and fictional. The data model is modeled on SAP HCM structures but does not use a real SAP system or real employee data.

## 1. Purpose

Payroll errors usually start upstream: an employee left in a closed position, a job classified Exempt while the person is set up as Hourly, a time sheet that doesn't match what payroll paid. This dashboard checks HR master data, time data, and payroll results against each other before a pay run is finalized. It lists each problem with a plain-English explanation and a suggested fix.

## 2. Scope

**In scope**
- 11 validation rules across Organizational Management / Personnel Administration (OM/PA) and Time & Payroll.
- A Streamlit dashboard with four working views (Org & Personnel, Time & Payroll, HR Overview, Testing & QA) plus Home and About.
- Excel export of exception lists.
- A reproducible synthetic dataset with planted defects, and automated tests proving each rule finds them.
- AI-assisted edge-case generation at development time, gated by human review.

**Out of scope**
- Connecting to a real SAP or HRIS system.
- Correcting data. The dashboard reports problems; fixes happen in the source system.
- Any AI calls at runtime.

## 3. Users

| User | Needs |
|---|---|
| HR / payroll specialist | See what is wrong, for whom, and what to do about it; export a work list. |
| HR / payroll manager | See the size and trend of data-quality issues; headcount and vacancy KPIs. |
| HRIS analyst / QA reviewer | Understand each rule's logic, verify that rules are correct and tested. |

The [User Guide](user_guide.md) is written for the first two groups.

## 4. Data model

Eight tables modeled on SAP HCM. Full definitions are in the [Data Dictionary](data_dictionary.md).

| Table | SAP analogue | Role |
|---|---|---|
| `org_units`, `jobs`, `positions` | OM objects O, C, S | Org structure |
| `employees` | PA infotypes 0000, 0001, 0002, 0007 | Who holds which position, and how they are classified |
| `wage_types` | Wage type catalog | Pay components (fictional codes 1000–1400) |
| `pay_periods` | Payroll periods | 6 biweekly periods, 2026-01-05 to 2026-03-29 |
| `time_entries` | Infotypes 2001/2002, CATS | Hours recorded per day |
| `payroll_results` | Results table RT | Hours and amounts paid per wage type |

The dataset (500 employees, 40 org units, 535 positions) is generated by [`data/generate.py`](../data/generate.py) with a fixed seed. It builds clean data first, then plants exactly 53 defects, recorded in [`data/planted_defects.csv`](../data/planted_defects.csv).

## 5. Validation rules

Each rule is one SQL file in [`sql/`](../sql/), run by DuckDB.

### 5.1 Output contract

Every rule returns one row per exception with the same columns:

| Column | Meaning |
|---|---|
| `rule_id` | e.g. `TP-01` |
| `severity` | `High`, `Medium`, or `Low` (see 5.3) |
| `emp_id` | Employee concerned (blank for a vacant position in OP-02) |
| `period_id` | Pay period (Time & Payroll rules only) |
| `issue` | One sentence describing the problem, with the specific values |
| `suggested_action` | One sentence telling an HR user what to do |

### 5.2 Rule definitions

| ID | Check | Logic | Severity | Row per | Planted |
|---|---|---|---|---|---:|
| OP-01 | Employee in an inactive position | Active employee whose position has status Inactive. | Medium | Employee | 6 |
| OP-02 | Position with missing or nonexistent org unit | Position whose `org_unit_id` is blank or not in `org_units`. | Low | Position | 4 |
| OP-03 | Two active employees in one position | More than one Active employee in a position. The earliest hire (then lowest ID) is treated as the rightful holder; each additional holder is flagged. | Medium | Extra holder | 3 |
| OP-04 | Terminated employee still in an active position | Terminated employee, Active position, term date before the as-of date. | High | Employee | 5 |
| OP-05 | Subgroup inconsistent with FLSA status | Hourly in an Exempt job, or Salaried in a Non-exempt job. | High | Employee | 5 |
| TP-01 | Paid vs recorded hours differ by more than 0.5 | Per employee and period: paid hours (wage types 1000–1300) vs recorded hours; flag if the absolute difference is greater than 0.5. Only compared when both time and pay exist. | High | Employee + period | 8 |
| TP-02 | Overtime paid to an Exempt employee | Wage type 1100 line for an employee whose job is Exempt. | High | Pay line | 4 |
| TP-03 | Hourly employee paid with no time entries | Active Hourly employee with pay in a period but no time entries dated within it. | Medium | Employee + period | 5 |
| TP-04 | Daily hours over 16 or negative | Time entry with hours above 16 or below 0. Exactly 16 and exactly 0 are allowed. | Medium | Time entry | 6 |
| TP-05 | Duplicate payroll line | More than one line for the same employee, period, and wage type. | High | Duplicated combination | 4 |
| TP-06 | Payment after term date | Payment date later than the employee's term date. Payment on the term date is allowed. | High | Pay line | 3 |

### 5.3 Severity

| Severity | Meaning | Rules |
|---|---|---|
| High | Pay may be wrong, or a compliance rule (FLSA) is broken. Fix before the next pay run. | OP-04, OP-05, TP-01, TP-02, TP-05, TP-06 |
| Medium | Record is wrong and could cause pay or reporting errors. | OP-01, OP-03, TP-03, TP-04 |
| Low | Data-quality issue with no direct pay impact. | OP-02 |

### 5.4 Design decisions

| Decision | Reason |
|---|---|
| **As-of date** = end of the last pay period (2026-03-29), not today's date. If no pay periods are loaded, today's date is used. | Results must be repeatable. A rule that compares against the system clock gives different answers on different days. |
| **TP-01 excludes wage type 1400** (shift differential). | Shift differential is a premium on hours already paid under 1000; counting its hours again would create false variances. |
| **TP-01 and TP-03 split the work.** TP-01 compares only employee-periods that have both time and pay; pay with no time at all is TP-03. | Each defect is reported once, by the rule that describes it best. |
| **OP-03 flags the later holder**, not both. | The later assignment is the one most likely to be the error; one row per problem keeps counts meaningful. |
| **Terminated employees hold no position** in clean data, and all terminations happen before the first pay period. | Mirrors SAP moving leavers to a default position, and keeps a normal final paycheck from looking like a TP-06 defect. |
| **FLSA status comes from the job** (via the position), not from the employee subgroup. | The job classification is the authority; the subgroup is what OP-05 checks against it. |

## 6. Functional requirements

| ID | Requirement | Page |
|---|---|---|
| FR-01 | Show a project summary, a synthetic-data disclaimer, and total exceptions by severity. | Home |
| FR-02 | Link to the GitHub repository and documentation. | Home, About |
| FR-03 | Show exception counts per OP rule as a bar chart. | Org & Personnel |
| FR-04 | Filter the OP exception table by rule, severity, and org unit. | Org & Personnel |
| FR-05 | Select a pay period; show recorded vs paid hours per period, and the difference. | Time & Payroll |
| FR-06 | Show the TP exception table for the selected period, filterable by rule and severity. | Time & Payroll |
| FR-07 | Download the currently filtered exception table as an Excel file. | Org & Personnel, Time & Payroll |
| FR-08 | Show KPIs: headcount, active positions, vacancy rate, total exceptions, % employees with any exception. | HR Overview |
| FR-09 | Show headcount by org unit and TP exceptions by rule per pay period. | HR Overview |
| FR-10 | Show planted-defect results (expected vs found) and the AI edge-case review status, from committed files only. | Testing & QA |
| FR-11 | Explain how the rules work and how to read the dashboard. | About |

**KPI definitions**
- *Headcount*: employees with status Active.
- *Vacancy rate*: Active positions with no Active employee ÷ Active positions.
- *% employees with any exception*: distinct employees appearing in at least one exception ÷ all employees (active and terminated).

## 7. Non-functional requirements

| Area | Requirement |
|---|---|
| Reproducibility | Data generation uses seed 42; regenerating gives byte-identical CSVs. Rules use the as-of date, not the clock. |
| No runtime AI | The deployed app makes no AI or network calls and needs no API key. |
| Performance | Data loading and rule results are cached with `st.cache_data`; all 11 rules run in well under a second. |
| Transparency | Each rule is a readable SQL file with a comment stating its intent. |
| Accessibility | Chart colors are validated for color-vision deficiency in light and dark themes; every chart has a data table view. |
| Privacy | Only synthetic data exists. Only synthetic data is sent to the AI provider during development. |

## 8. Testing strategy

| Layer | What it proves | Where |
|---|---|---|
| Planted-defect regression | Each rule finds exactly the planted count (53 total). | `tests/test_rules.py` |
| Clean-data check | Each rule finds zero exceptions in the data before planting. | `tests/test_rules.py` |
| Boundary unit tests | Thresholds behave as specified (16 h, 0.5 h variance, payment on term date). | `tests/test_rules.py` |
| Structured scenarios | 22 documented scenarios, including real dashboard runs with filters applied. | [`test_scenarios.md`](test_scenarios.md), `tests/test_scenarios.py` |
| AI-assisted edge cases | AI proposes boundary cases; a human accepts or rejects each; accepted cases run as tests. | [`ai_testing_log.md`](ai_testing_log.md), `tests/test_ai_edge_cases.py` |

No test calls an AI API, so the whole suite runs offline and gives the same result every time.

## 10. Future enhancements

GitHub Actions running the tests on every push; a "mass correction" simulator for OM/PA rules; a year-end check page (YTD totals vs sum of periods); a process map of the pay-period validation workflow; a defect log using GitHub Issues; an AI script that drafts a GitHub Issue from a failing test.
